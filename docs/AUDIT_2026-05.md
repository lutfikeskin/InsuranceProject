### 1.2 Critical dependency chains

- **Cache-version hash chain** (intentional): `modules/extraction/cache_version.py` reads `modules/extraction/prompts.py` + `modules/extraction/schemas.py` to derive `CACHE_VERSION`. Any edit to either file invalidates extraction caches — by design. **Do not duplicate hash logic elsewhere.**
- **PolicyHistory late import**: `app.py:11` imports `core.history_model` purely to register the SQLAlchemy model. If `core/services.py` later imports `history_model` early in module load, a circular-import bomb is possible. Mitigation today: late import works; long-term: an explicit `init_models()` call in `app.py` would be cleaner. **No action this branch.**
- **Pipeline helpers** are now split into 12 sibling modules under `modules/extraction/` (per CLAUDE.md's blast-radius map). The pipeline.py file orchestrates; helpers do the work.

### 1.3 Confirmed seams (informational only)

The codebase has tight coupling to "auto + GL + COI" assumptions. The seams below are where that coupling lives. **They are not bugs given the current product scope** — they would only need to flex if a fundamentally different product (Workers Comp, Commercial Property) were added. Documenting them here so a future developer knows where to push.

## 2. Modularity Seams (Documentation Only)

> **Scope note:** No new product types are planned. We do **not** introduce a `ProductRegistry`, plugin protocol, or per-product schema/prompt directories on this branch. The list below is a future-developer's map.

### 2.1 Policy-type enum lives in three places

- `modules/extraction/schemas.py:10-26` — `CLASSIFICATION_SCHEMA` enum hardcodes 8 policy types.
- `modules/extraction/cache_version.py:13-16` — `POLICY_TYPE_ENUM` derives from the schema. Adding a new policy type auto-invalidates **all** extraction caches.
- `core/services.py:44-54` — `ACCOUNT_TYPE_BY_POLICY` dict maps policy → account type.

**If you add a new policy type:** all three lists must agree. Today they agree only by convention. A `core/policy_types.py` enum imported by all three would centralize the truth.

### 2.2 Coverage ontology is flat and auto/GL-centric

- `core/coverage_ontology.py:28-44` — `POLICY_TYPE_CONSTRAINTS` hardcodes family→policy-type allow-lists.
- `core/coverage_ontology.py:80-150` — flat `COVERAGE_REGISTRY` of coverage codes.

**If you add Workers Comp:** codes like `WC_BODILY_INJURY_BY_DISEASE` would collide or require awkward prefixing. The registry would need a `product → codes` namespacing layer.

### 2.3 Prompt monolith

- `modules/extraction/prompts.py:74-256` — `get_extract_all_prompt()` is ~180 lines, hardcoded for auto / GL / COI structure.

**If you add a new product:** today you'd edit this function or fork it. A `ProductPromptProvider` protocol with per-product implementations would isolate edits. Out of scope this branch.

### 2.4 Auto-only validation rules

- `modules/extraction/extraction_assembly.py:34-54` — `apply_auto_liability_rules()` early-returns for non-auto policy types.
- `modules/extraction/coverage_backfill.py` (entire file) — assumes auto flat fields: `liability_limit`, `cargo_limit`, `um_uim_limit`, `med_pay_limit`. A Workers Comp policy (`class_code`, `payroll`, `experience_mod`) has nowhere to land in this file.

**If you add a non-auto product:** these helpers need a strategy-pattern split (per-product validator + per-product backfill).

### 2.5 Schema construction branch

- `modules/extraction/schemas.py:296-331` — `build_complete_policy_schema()` branches on `policy_type` and falls through to `COMPLETE_POLICY_SCHEMA` for anything that's not personal auto.

**If you add a fundamentally different shape** (Workers Comp class-code-driven rating, Property locations & blanket limits), the fall-through schema is wrong and you need a per-product schema callable.

### 2.6 Reporting assumes ACORD 25

- `reporting/acord_view.py` (185 LOC) — hardcoded ACORD 25 certificate structure. Workers Comp and Property would use different ACORD forms.

## 3. Dead Code & AI-Slop Inventory

This is what gets **executed** on this branch (Phase 2). Each item below maps to a planned commit.

### 3.1 Duplicate text helpers (will be consolidated)

- `modules/extraction/extraction_response.py:43-53` — `_clean_text()` local helper.
- `core/services.py:242-263` — `_clean_text()` and `_clean_limit_text()`, near-identical logic.

**Plan:** consolidate into `utils/text_utils.py` (already exists at 251 LOC of vehicle utils — wait, that's `utils/vehicle_utils.py`; `utils/text_utils.py` already exists separately, confirmed in the file inventory). Both callers import the shared version. Single source of truth.

### 3.2 Single-use helpers obscuring call sites

- `modules/extraction/extraction_response.py:66-86` — `_parse_us_address()` defined 20 lines for one call site at line ~117.

**Plan:** inline at the call site unless a second caller is discovered. If the logic is worth keeping as a helper, move it to `utils/text_utils.py` with a comment explaining the COI-specific address split rule.

### 3.3 Silent exception swallows (will be tightened, not deleted)

Each of the following catches too broadly and returns `None` / `{}` / a stringified error, making caller-side success vs. failure indistinguishable. The plan is to **narrow** the except clauses to the specific expected exceptions and **log with context**, not to delete the safety net.

| File:line | Today's behavior | Fix direction |
|---|---|---|
| `app.py:38` | Bare `except:` around `st.secrets` access | Catch `KeyError`/`FileNotFoundError` only; log key name |
| `modules/extraction/auditor.py:44` | Bare `except:` in date parse | Narrow to `(ValueError, TypeError)`; log offending value |
| `modules/extraction/gemini_transport.py:89-90` | `except Exception: pass` in cache-expiry check | Narrow to `(KeyError, ValueError)`; cache-miss is a known signal |
| `modules/extraction/extraction_local_cache.py:89-90` | `except Exception:` returning `None` | Narrow and log; preserve `None` only for "not found" |
| `core/variant_tracker.py:23-24, 35-36, 44-45, 128-130, 148-150` | **Five** sibling try/excepts that log+swallow | Replace with a single `_safe_load_state()` returning `(state, error)` |
| `core/services.py:1457-1458, 1665-1666` | `return None, f"Error: {e}"` | Return a typed result (`SaveResult(ok=False, error=ExceptionInfo)`) or re-raise |
| `modules/coi/generator.py:16-27` | Nested try/except for a JSON load | Single narrow `FileNotFoundError` catch; let `JSONDecodeError` raise |

**Acid test at every site:** *can the caller distinguish success from failure after this change?* If not, the fix is incomplete.

### 3.4 Two-path classification entry

- `modules/extraction/pipeline.py:507` — `_classify_policy()`.
- `modules/extraction/pipeline.py:542` — `_classification_with_user_policy_type()` wraps the above for one user-hint code path.

**Plan:** the second is a parameter, not a separate function. Collapse to a single `_classify_policy(text, user_policy_hint: str | None = None)` entry point. Update `tests/test_prompt_routing.py` if it exercises the wrapper directly.

### 3.5 Dead import / unwired UI

- `views/database_page.py:8` — `create_excel_report` imported from `utils/exporter.py`, never called. Either wire it to a real "Export" button (planned in Phase 4.2 alongside the sortable table) or delete the import.
- Broader `ruff --select F401` sweep across `views/` and `modules/` — apply manually after review (no auto-fix on a code-quality audit).

### 3.6 Confirmed-not-dead (do not touch)

For the record, the following looked suspicious during exploration but **are** in use; leave them alone:

- `modules/extraction/extraction_assembly.py` — `apply_auto_liability_rules()`: yes, it early-returns for non-auto, but the early-return is *correct* given current scope.
- `modules/extraction/auditor.py` — premium sanity audit. Real callers exist.
- `modules/extraction/coverage_backfill.py` — locked-in regression fix from commit `d8df149`. Phase 3.4 adds tests so it cannot regress.

## 5. UI/UX Inventory

### 5.1 Page-by-page

**`app.py`** (172 LOC) — entry, sidebar, settings dialog
- API-key entry has no test-on-save validation. User can paste a wrong key and not learn until extraction fails.
- `st.session_state["GEMINI_API_KEY"]` is set once, never cleared. **No logout / clear-key control.** → fixed in Phase 4.4.

**`views/dashboard.py`** (187 LOC) — KPI overview
- No "last refreshed at" timestamp or time-zone note for the daily usage reset.

**`views/database_page.py`** (664 LOC) — customer + policy browse
- Customers rendered as expandable rows; **not sortable**, **not filterable by status/carrier/date**. → fixed in Phase 4.2.
- `create_excel_report` imported but unused (line 8). → wired or removed in Phase 2.5 / 4.2.
- Update buttons keyed by `f"updatename_{customer.id}"` — stale keys if a DB is rebuilt with overlapping IDs; low risk in practice.

**`views/process_policies.py`** (1458 LOC) — the workhorse
- Upload → extract → review → save in one file.
- Confidence values exist in extracted data but **are not surfaced on the review screen**. They only show inside `edit_dialog.py`. → fixed in Phase 4.1.
- No "clear extraction state" control; same upload twice creates ambiguity.

**`views/create_coi.py`** (514 LOC)
- Good session-state cleanup pattern at lines ~50-60 (clears `coi_desc_area_*` when policy changes — keep this).
- "Generate & Download PDF" vs. "Generate Bulk COIs" — verb tense inconsistent. → Phase 4.6.
- No double-submit guard; rapid clicks can produce duplicate PDFs.

**`views/edit_dialog.py`** (298 LOC) — 6-tab modal
- Each tab is its own `st.form()`. There is **no "Discard changes" control**; the only way out is the OS-level dialog close. → fixed in Phase 4.3.
- Tab-by-tab forms mean a save in one tab does not reflect into another tab's view until the dialog reopens. Document; do not fix this branch.

**`reporting/acord_view.py`** (185 LOC)
- Pure data transform, no UI. ACORD 25 hardcoded (see §2.6).

### 5.2 Cross-page consistency

- **Terminology drift**: "Policy" / "Document" / "Submission" used interchangeably across views.
  → Phase 4.5 sweep: **Policy** = DB entity, **Document** = uploaded PDF, **Submission** is retired as ambiguous. Visible labels only — no DB field or session-state key renames.
- **Success toast wording**: `st.success("Settings saved")` vs. `st.success("Successfully generated")` — inconsistent voice. → Phase 4.6 standardizes on imperative-past ("Saved.", "Generated.", "Updated.").
- **Button label drift**: "Save & Refresh" vs. "Update" vs. "Save". → Standardize on "Save" unless a side-effect needs to be advertised.

### 5.3 Session-state hazards (none fixed beyond Phase 4)

- `db_engine` (app.py:25) — set once, never cleared. Fine; document.
- `GEMINI_API_KEY` — Phase 4.4 adds a clear control.
- Dynamic-suffix keys (`coi_desc_area_{policy_id}`, `updatename_{customer.id}`) — never garbage-collected. Documented risk; no fix this branch.
